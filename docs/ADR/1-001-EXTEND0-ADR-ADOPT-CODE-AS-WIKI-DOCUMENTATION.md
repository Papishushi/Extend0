# ADR 1-001: Adopt Code-as-Wiki Documentation

## Status

Accepted

## Date

2026-05-24

## Context

Per ADR 1-000, Extend0 major `1` needs a durable documentation system that can live in Git, survive repository evolution, and remain readable to both humans and AI tooling.

The repository already uses a structure compatible with wiki-style navigation, including `Home.md` and `.order`. However, the repository is hosted on GitHub, so the documentation cannot depend on Azure DevOps rendering behavior to remain useful.

Extend0 also has multiple documentation audiences with different needs:

- consumers who need supported behavior, usage guidance, and conceptual orientation
- contributors who need architectural rules and development conventions
- AI agents that need stable conceptual entry points before reading implementation code

Without clear rules, those audiences tend to get mixed into the same pages, which leads to drift, contradiction, and low-trust documentation.

## Decision

Extend0 adopts `docs/` as a code-as-wiki documentation system under repository major `1`.

The documentation model is GitHub-first while retaining the `Home.md` and `.order` conventions already present in the repository.

The following decisions are normative:

- documentation language defaults to English
- top-level docs landing pages are canonical navigational entry points
- `docs/ADR.md` is the ADR index page
- `docs/ADR/` is the canonical location for architecture decisions
- documentation must remain useful when read directly from the GitHub repository, without relying on Azure-specific wiki rendering behavior

The code-as-wiki model is intentionally lightweight:

- content is stored as Markdown in the repository
- navigation is explicit rather than generated by a special platform
- wiki affordances are allowed when they degrade gracefully in GitHub

## Audience Model

The documentation set is organized around primary audiences:

- `Home.md` is for first contact and navigation
- `Requirements.md` is for product and capability framing
- `Runtime.md` is for runtime behavior and operational concepts
- `Extensions.md` is for extension points and advanced integration
- `Deployment.md` is for deployment-facing usage and environment concerns
- `ADR.md` and `docs/ADR/` are for development governance and durable decisions

When a page targets multiple audiences, it must say so explicitly near the top of the document.

## Conventions

### Required Top-Level Pages

The top-level documentation set must contain these landing pages:

- `Home.md`
- `Requirements.md`
- `Runtime.md`
- `Extensions.md`
- `Deployment.md`
- `ADR.md`

### Navigation Rules

- `docs/.order` defines the intended top-level navigation order.
- Subsections may use local `.order` files when ordered child navigation matters.
- Landing pages should act as stable entry points even when child pages expand over time.

### Editorial Rules

- Every landing page must state its purpose, intended audience, and child-document map.
- Filenames must be stable, descriptive, and Markdown-based.
- Documentation should prefer durable concepts, contracts, and supported behavior over transient implementation notes.
- Consumer-facing documentation should be separated from development governance unless the page clearly labels both audiences.

Additional editorial expectations:

- lead with concepts, then behavior, then details
- prefer terminology consistency over stylistic variation
- define terms once and reuse them consistently across pages
- avoid embedding roadmap speculation in consumer-facing docs unless the page is explicitly forward-looking
- avoid using docs pages as temporary scratchpads for unresolved implementation work

## Structural Conventions

- top-level landing pages are stable anchors and should rarely be renamed
- child pages may expand beneath those anchors as the system grows
- if a section becomes too large, split it into child pages rather than overloading the landing page
- cross-links between pages should favor stable relative Markdown links
- `.order` files express intended reading/navigation order but must not be the only way a document can be understood

## Non-Goals

This ADR does not require:

- adopting a static-site generator in this phase
- mirroring Azure DevOps wiki rendering exactly
- replacing `README.md` as the public repository entry point
- documenting every implementation detail immediately

## Consistency Rules

- Docs must not knowingly contradict `README.md`; if they diverge, a follow-up alignment change is required.
- Consumer docs describe supported behavior, usage expectations, and conceptual guidance.
- ADRs describe governing decisions, repository-wide policy, and architectural rules.
- Development conventions belong in ADRs or in explicitly development-facing documentation pages, not mixed into consumer pages without clear labeling.

Consistency should be interpreted as follows:

- if the README is the first-contact summary, docs may elaborate but should not silently redefine it
- if supported behavior changes, the corresponding consumer docs should be updated in the same change or immediately after
- if a repository-wide rule changes, an ADR should be the authoritative place that records the change

## Change Triggers

A new ADR or an ADR update should be considered when documentation changes would:

- alter the top-level section model
- redefine the intended audiences of major doc sections
- replace GitHub-first assumptions with a platform-specific documentation system
- change ADR location, numbering, or interpretation

Routine content additions inside the established documentation structure do not require a new ADR.

## Consequences

- Extend0 gains a documentation system that works well in GitHub while remaining compatible with the wiki-style structure already in use.
- Future documentation growth is guided by stable landing pages instead of ad hoc file sprawl.
- ADRs become the normative place for durable rules, while consumer pages remain focused on product understanding and usage.
- Any future change to these conventions must remain compatible with ADR 1-000 or explicitly supersede it.

Operationally, this means future docs work should usually answer three questions:

- who is this page for
- what durable concept does it explain
- why does it belong in docs rather than an ADR or inline code comment
